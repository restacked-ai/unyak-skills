# /unyak-plan — Project planning

Unyak maintains AGENTS.md so the coding agent always has the right context. This skill makes AGENTS.md good enough to be worth maintaining — it does the thinking before building starts.

**Output:** `AGENTS.md` at project root, populated with intent, constraints, user goals, and explicit scope boundaries.

Run this when the project idea needs more than a quick interview to be useful to a coding agent. The quality check at the end is: "Could a coding agent produce a coherent first build from this AGENTS.md with zero additional context?"

After this skill completes, run `/unyak-start` to initialize the `.unyak/` tracking directory. unyak-start will detect the populated AGENTS.md and skip the interview.

## How to run this skill

Work through the parts in order. Do not skip ahead. Confirm with the user after each part before moving to the next. One question at a time — no multi-part prompts.

**Before asking anything:** read the project. Check for package.json, README, existing code, and git log. Use what you find to skip obvious questions and phrase the remaining ones in context. Never ask for something you can already see.

**Who owns what:** The user owns intent (goals, pain, stories, choices). You own derivation (app concept, feature list, gap spotting, AGENTS.md generation). User-owned content needs explicit confirmation before proceeding. Your derived content needs review, but you propose first and the user reacts.

---

## Part 1: Goal Tier

Ask this first. Always. Before anything else. The tier determines which questions get asked downstream, what belongs in scope, and what goes in "Explicitly Out of Scope."

Present the tiers and ask the user to pick one:

| Tier | When |
|------|------|
| Demo only | Pitching to stakeholders or sponsors this week |
| Demo + continue | Pitch now, might keep building if there's interest |
| Prototype only | Test with one real user group, then decide |
| Prototype + continue | Run something real, plan to keep building |
| Production MVP | Launch publicly with a tight, defined scope |
| Production open-ended | Build a real product, scale, maintain |

**Output format:**
```
## Goal Tier
**Tier:** [selected tier]
**Why:** [1 sentence on why this tier fits]
```

Confirm, then move to Part 2.

---

## Part 2: Creative Brief

Seven fields. The last one is auto-generated by you.

Ask for each field that isn't already clear from the README or prior context. Skip or pre-fill what's already evident.

| Field | What to ask |
|-------|-------------|
| Target user | Who specifically uses this? Push for a concrete persona, not "everyone." |
| User goal | What are they trying to accomplish in their life or work? Not the app's goal — theirs. |
| Pain | What hurts about the current way they do it? Push for specific ("takes 2 hours") not vague ("it's annoying"). |
| Cause | (Optional) Why does the pain exist? Sharpens the solution. Skip if not needed. |
| Solution | How does the app remove or reduce the pain? One or two sentences. |
| Memorable moment | The one thing someone will remember. For demos: the wow. If the user can't name one, accept TBD and flag it as a risk. Do not block progress. |
| App concept | Auto-generate from the fields above. A short paragraph describing what the app is and the core value. Regenerate if any field changes. |

**Multi-persona note:** If the user names more than one target user, push for the primary one (whoever opens the app most often). Note secondary users if they materially shape the product.

**Output format:**
```
## Creative Brief

### Target User
[1-3 sentences]

### User Goal
[1-2 sentences]

### Pain
[1-3 sentences]

### Cause
[1-2 sentences, or omit]

### Solution
[1-2 sentences]

### Memorable Moment
[1 sentence, or "TBD — flagged as a risk"]

### App Concept
[1 short paragraph, auto-generated]
```

Present, ask "Anything to change?", then move on.

## Part 3: User Journey

Map the end-to-end flow before writing stories. Stories say what users want to do; the journey says when, in what order, and in what context.

Ask: "Walk me through the app from the moment someone lands on it to the moment they've gotten what they came for."

If the user describes a journey, capture it as numbered steps. If not, prompt: "What's the first thing they see? Then what? Then what?"

For each step, note: where the user is, what they do, what the app does in response.

**Scope by tier:**
- Demo only: the journey should match what the demo will actually show. Don't spec steps that won't be built.
- Prototype+: can include partially built or deferred steps — mark them "(Roadmap)".

**Output format:**
```
## User Journey

1. **[Step name]:** [What the user sees and does. What the app does in response.]
2. **[Step name]:** [...]
3. **[Step name]:** [...] (Roadmap)
```

Present, confirm, move on.

---

## Part 4: User Stories

Numbered list of plain statements. No "As a [user], I want..." template. No acceptance criteria. Just clear, direct statements of what the user wants to do.

Read the Creative Brief and User Journey. Ask: what does this user need to be able to do to get their goal met? Each story is one action or capability.

Aim for 8–15 stories. Fewer means scope is too thin. More means you're listing features — collapse them.

If there are primary and secondary users, group stories by persona.

**What good looks like:**
- "Save a draft and come back to it later."
- "See all my events in one place."
- "Share a link with someone who doesn't have an account."

**What to avoid:**
- Engineering tasks ("Set up Postgres")
- Vague aspirations ("Have a great experience")
- Features in disguise ("Use the drag-and-drop UI")

**Output format:**
```
## User Stories

1. [Plain statement]
2. [...]
```

Present, ask for additions or removals, move on.

---

## Part 5: Technical Context

Use the tier from Part 1 to decide which questions to ask. The goal: give the coding agent a technical envelope so it doesn't over-engineer a demo or under-engineer a production build.

**For Demo only — ask these:**

| Question | What to ask |
|----------|-------------|
| Frontend tool | Which agent or framework are you building with? (Lovable, v0, Bolt, Cursor, other) |
| Platform | Mobile-first, desktop-first, or responsive? |
| Visual style | Pick one from the menu below — or describe your own with a reference site. Do not leave this open. |
| Data approach | In-memory only, browser localStorage, or hardcoded JSON? |
| Runtime | Preview link only, local only, or single hosted deployment? |

**For Demo only — Constraints and integrations:** Skip by default. If the user mentions a specific integration the demo needs to show, capture it as one line. Otherwise: "None — demo tier."

**For Prototype + continue:** Ask Demo questions plus: "Will any content be locked and injected from an external source (admin-defined rules, imported files)?" If yes, capture as a constraint.

**For other tiers:** Ask the Demo questions as a baseline plus obvious additions for the tier. Flag that this tier's full question set is still being refined.

**Visual style menu:**

Present as a list. Explain: "Picking a specific style prevents the agent from defaulting to 'modern and clean' — which is what every AI app looks like."

- **Brutalist / raw** — Stark, oversized text, harsh contrast. Both platforms.
- **Editorial / magazine** — Big typography, generous whitespace. Best on desktop.
- **Glassmorphism / Apple-modern** — Frosted glass, soft shadows. Native to mobile/iOS.
- **Soft pastel / playful** — Rounded shapes, soft colors. Both platforms.
- **Terminal / monochrome** — Monospace font, dark background, single accent. Best on desktop.
- **Luxury / refined** — Minimal, serif fonts, muted tones. Both platforms.
- **Custom** — Ask for one reference site.

If the user picked Mobile-first: note that Terminal, Editorial, and Brutalist styles translate poorly and suggest alternatives.

**Platform implications to write into output:**
- Mobile-first: touch targets ≥44px, bottom navigation, one column, no hover-only interactions, test at 375px
- Desktop-first: hover states allowed, sidebar navigation, test at 1440px
- Responsive: build mobile-first, add desktop enhancements at breakpoints

**Explicitly skipped at this tier** (write these into Technical Context — the agent needs to know what NOT to build):

Demo only:
- Authentication (mock role picker if roles are needed)
- Real database (use chosen data approach instead)
- Dynamic AI responses (all signals hardcoded)
- Secrets management
- Analytics

**Output format:**
```
## Technical Context

**Tier:** [from Part 1]

### Build choices
- **Frontend tool:** [answer]
- **Platform:** [answer]
- **Visual style:** [chosen option — 1 sentence on feel. Reference site if provided.]
- **Data approach:** [answer]
- **Runtime:** [answer]

### Constraints and integrations
[For Demo only: "None — demo tier." Or one line if specific integration needed.]

### Platform implications for the agent
[Bullet list matching chosen platform]

### Explicitly skipped at this tier
[Bullet list from tier table above]
```

Present, confirm, move on.

## Part 6: Feature List

Each feature has three things: Name, Description (1–2 sentences), Dependencies (which features must exist first, or "None").

Map user stories to features. One story can map to one feature or multiple, and vice versa — don't force 1:1.

Then map dependencies honestly. A feature depends on another only if it can't function without it. Don't invent dependencies (over-coupling) and don't skip real ones (build will stall).

Cross-reference Part 1 (tier) and Part 5 (technical context) for each feature: Does this tier need this feature? Does the technical context change the implementation? Note tier-specific simplifications inline.

**Output format:**
```
## Feature List

### [Feature Name]
- **Description:** [1-2 sentences. Note tier simplifications inline.]
- **Dependencies:** [Feature name, Feature name] or None
```

Present, ask for edits, move on.

---

## Part 7: Open Questions and Gaps

Surface what's known to be unknown. Agents fill gaps silently — this section makes gaps explicit so a human resolves them, not the agent.

**Bar is tier-aware:**
- Demo only: most demos have few real gaps. Write "None known at this tier." if the user has nothing to add. Don't invent gaps.
- Higher tiers: push harder.

Ask: "Anything you know you don't know yet? Stuff that's still vague, decisions you've deferred, things you're hoping the agent will figure out?"

Then scan the brief, journey, stories, features, and technical context yourself. Propose gaps the user didn't mention. If the user says "nothing," accept it but log the ones you spotted — mark them "Skill-spotted, unresolved."

**Output format:**
```
## Open Questions and Gaps

### User-flagged
1. [Question or unknown]

### Skill-spotted (unresolved)
1. [Question spotted, not yet answered]
```

Present, confirm or dismiss entries, move on.

---

## Part 8: Roadmap

Capture out-of-scope items explicitly. Good ideas that don't belong in this build go here, not in the feature list.

Collect from: journey steps tagged "(Roadmap)", features deferred during the feature list conversation, items that belong to a higher tier.

**Output format:**
```
## Roadmap

1. [Feature name.] [1 sentence on what it does and why it's deferred.]
```

Present, confirm, move on to Quality Check.

---

## Part 9: Quality Check

Run this after the Roadmap. Catches common PRD failures before handoff to a coding agent. Do not skip even if everything looks fine.

Score the PRD yourself. The user reviews and accepts or pushes back.

**Rubric:**

| Criterion | Weight | What to check |
|-----------|--------|----------------|
| Tier fit | 15 | Does scope match tier? Demo with full auth is too much. Production with mocks is too little. |
| Pain clarity | 10 | Is pain specific and concrete? Vague pain produces vague apps. |
| Journey completeness | 10 | Does journey cover full flow from landing to outcome? Any missing steps? |
| Story quality | 10 | Are stories plain user needs? Not engineering tasks, not features in disguise. |
| Feature scope | 15 | Reasonable count for tier? No UI elements (buttons, screens) as standalone features? |
| Dependency honesty | 15 | Real dependencies only. No invented ones, no skipped ones. |
| Explicit skips | 10 | Does Technical Context name what's deliberately skipped at this tier? |
| Tech context completeness | 10 | All 5 tech context questions answered (tool, platform, style, data, runtime)? |
| AGENTS.md readiness | 10 | Is the technical context specific enough to produce a clean AGENTS.md? |
| Memorable moment | 5 | Defined, or explicitly flagged as TBD with a risk note? |

**Scoring:**
- A (90–100): Ready to hand to a coding agent.
- B (75–89): Ready with minor gaps noted.
- C (60–74): Fix flagged items before handoff.
- D (40–59): Significant rework needed.
- F (0–39): Restart. Inputs are too weak.

For each criterion, assign a score with one sentence of justification. Be honest, not generous.

**What happens next:**
- A or B: Proceed to AGENTS.md generation.
- C: Propose specific fixes. Offer to re-run the failing part. Do not proceed until user explicitly accepts.
- D or F: Stop. Identify the weakest part and offer to redo it.

**Output format:**
```
## Quality Check

**Score:** XX/100 (Grade: X)

| Criterion | Score | Notes |
|-----------|-------|-------|
| Tier fit | X/15 | [1 sentence] |
...

**Issues to fix:**
- [Specific issue]

**Suggested fixes:**
- [Actionable change pointing to the part to revise]
```

## AGENTS.md Generation

Run after a passing Quality Check (A, B, or explicitly-accepted C).

**AGENTS.md is the primary deliverable.** It is not a summary of the PRD — it is an instruction set derived from it. The test: could a coding agent produce a coherent first build from this file with zero additional context?

**What to include:**
- Project overview (1 short paragraph: what it is, who it's for, what problem it solves)
- Goal tier
- Target user (1–2 sentences)
- Core problem (2–3 sentences — pain, cause if known, how the app addresses it)
- Tech stack (only if it contains constraints; don't list things obvious from project files)
- Visual style (with reference if provided)
- Platform (with agent-facing implications: touch targets, navigation pattern, tested viewport)
- Data approach
- Feature behavior (how each feature works, not what it is — decision-level detail)
- Explicitly out of scope (bullet list, with instruction: "Do not build. If scaffolded automatically, remove.")
- Working Mode (current phase and focus)

**What to exclude:**
- Creative brief narrative
- User journey prose
- Roadmap items
- Quality check results
- Open questions (unless they directly constrain the build)
- Folder structure, code blocks, schema definitions, type definitions — anything the agent can read from the project files directly

**Content discipline:** Apply this rule to every section you write. If the next agent could find it by reading a project file in under 30 seconds, don't put it in AGENTS.md. Drift is worse than incompleteness. Replace discoverable content with a pointer ("see `src/types/` for data shapes").

**Output:** Write `AGENTS.md` to the project root. Present it to the user before writing and confirm.

---

## Style rules

- No em-dashes. Use commas, parentheses, or sentence breaks.
- No emojis.
- No filler ("Great question!", "I'd love to help.").
- Short sentences. Direct language.
- No tables in output unless genuinely clearer than prose.

---

## Edge cases

**User pastes a half-finished brief.** Extract whatever fields are filled. Ask only for missing ones. Confirm extracted values before using. Still ask for goal tier separately if it's not in the input.

**User wants to skip to features.** Push back once: features without a tier and brief produce drift. If they insist, ask the tier question at minimum, then generate a one-paragraph implicit brief from their feature ideas and confirm before continuing.

**User has 30+ features in mind.** Ask which 5–8 are essential to validate core value. The rest go in the Roadmap. A demo should never have 30 features.

**User can't articulate the pain.** Ask: "What does the user do today that's slow or broken?" If they still can't answer, the idea isn't ready. Say so directly.

**User can't define the memorable moment.** Accept TBD. Mark it as a risk in Open Questions. Flag it again in the Quality Check.

**User picks a tier still marked "To be defined."** Fall back to Demo only questions plus obvious additions for the stated tier. Flag to the user that this tier's full question set is still being refined. Proceed.
